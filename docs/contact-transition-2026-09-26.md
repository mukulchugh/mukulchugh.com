# Contact booking open/close transition

Replaces the jittery Contact booking open/close animation (`components/contact/contact-section.tsx` / `.module.css`) with an element-scoped native View Transition. Root cause: CSS simultaneously interpolated grid columns, heading/subheading font-size, header min-height/padding, and the calendar reveal row while other properties (flex-wrap, width, button label) snapped instantly, producing reflow-driven jumps. (A separate, earlier FLIP-transform candidate for this same bug was independently measured and rejected for a 224px paragraph jump — cited here only as evidence of the general class of defect, not a measurement of this fix.)

All work is in `components/contact/`, plus one explicitly-authorized narrow companion selector change in `components/navigation/genie-window.module.css` (see below) required by the new outer wrapper — no genie-window geometry or timeline logic was touched.

## Approach

`Element.prototype.startViewTransition` (Chrome 147+, present in this environment's Chromium 151) is called on the `<section>` tile itself — never `document.startViewTransition`, which would cover the dock.

- **Panels** (`.statement`, `.call`, the tile itself) each get a `view-transition-name` and share `view-transition-class: contact-vt-panel`. Their background/geometry is allowed to morph as a bitmap (the native default crossfade+resize) since all live text is excluded onto its own named leaf.
- **Leaves** (heading, lede, icon, call title/subtitle, book button, utilities row) are named individually (`contact-vt-leaf`) and render their old/new snapshots at **intrinsic size** (`object-fit: none`) so a resizing group never stretches or magnifies glyphs — an earlier candidate's actual defect (inflated "Back" glyphs, ~3x). The old copy fades out quickly, the new copy resolves in over the remainder, with no overlap between the two windows — a simultaneous cross-dissolve visibly double-exposes two different-size headings.
- **Calendar reveal** gets its own name/class (`contact-vt-reveal`) so it isn't flattened into `.call`'s panel bitmap (which otherwise looks like a shrinking miniature calendar); its old snapshot fades out quickly instead of lingering.
- Existing CSS transitions on `.call`/`.shader`/`.reveal` are suppressed for the duration of a native transition (`.tile[data-vt-active="true"] * { transition: none !important; }`) so they can't keep animating an in-between state into the "new" snapshot and fight the view transition.
- An outer `.frame` wrapper clips (`overflow: clip; border-radius: 14px`) and carries the tile's border/background; its `height` is grown/shrunk via a WAAPI animation (started once `transition.ready` resolves, targeting the frame rather than the tile) so the card border and the content below it don't hard-snap while the panels are still animating.
- Unsupported browsers and `prefers-reduced-motion: reduce` (checked at click time and via a live `matchMedia` listener) skip `startViewTransition` entirely and call `setBooking` directly — an instant, honest cut.

## Corrections made during review

A coordinator review caught several real defects, all fixed before landing:

- **Wrong `getComputedStyle` scope.** `getComputedStyle(document.documentElement, pseudo)` returns UA defaults for an element-scoped transition; it must be scoped to the transition-root element. This had led to a wrong conclusion that class-based `view-transition-class` selectors don't work on `::view-transition-old()/-new()` (they do) and a since-reverted, unnecessary per-instance `<style>`-tag workaround.
- **Height-animation snapshot contamination.** Creating the frame's height animation inside the transition's `update()` callback applied its first keyframe before the native "new" snapshot was captured, corrupting it back toward the old height. Fixed by creating it only after `ready` resolves, targeting the separate `.frame` (not the tile's own grid, which was also found to let an unrelated `getComputedStyle` read resync the captured height mid-animation).
- **Stale-transition races.** The generation counter is now bumped, and the previous transition skipped, on *every* `applyBooking` call (including the immediate/reduced-motion branch) — previously a superseded transition's deferred `update()` could still apply stale state after a newer intent had committed. Escape reads the synchronous `bookingRef` (not React state, which lags the deferred `update()`), so pressing it right after opening cancels that pending open instead of bubbling to a dock window's own close handler.
- **Unscoped `startTime` donor.** The height animation aligned its start to the first animation anywhere on the page with a numeric `startTime`, which could be unrelated (dock/shader/entrance). Scoped to this section's own `::view-transition-*` pseudo-element animations.
- **Border snapped instantly.** The tile is the transition root; its own live box is never masked by the snapshot overlay (unlike its named descendants), so anything painted directly on it — its border/background — still updated at the tile's real, instantly-final geometry while the frame and panels were still animating around it. Moved border/background/radius onto `.frame`, whose height is the one actually animated (measured the frame/panel bottom-edge gap converging from ~144px at 60ms to ~0px by 320ms).
- **Leaf fade split.** Tried a 55/45 overlapping split (visibly double-exposed) and then an exact 50/50 non-overlapping split (fixed the double-exposure, but its single-instant crossing point landed exactly on `duration/2`, a common inspector sampling point, so both my own probe and the coordinator's inspection reliably paused on that exact frame). Settled on an asymmetric 40/60 split, still with zero overlap.
- **`afterHeight` read from the wrong element.** Read from the borderless `section` instead of `.frame` (which carries the border), landing 2px short and popping on cleanup. Fixed to read the frame's own height.
- **Dock's Contact styling depended on the old DOM ancestry, in two passes.** `genie-window.module.css` strips Contact's own border/radius and stretches it to fill the dock window via the structural selector `.content > div > section`; the new `.frame` wrapper added a nesting level that silently broke it, so it was extended to `.content > div > div` / `.content > div > div > section`. That first pass only checked the `.frame` wrapper's own height and wrongly reported the dock as fully fixed: `.frame` filled (its `min-height: 100%` happened to resolve against `.content`), but the actual `<section>` inside it did not (closed-state height ~604px against a ~738px window) -- `min-height: 100%` on a child can only resolve against a parent whose own height is *definite*, and `.frame`'s height is deliberately only a `min-height` (so tall booking content can grow it and let `.content`'s own scrollbar handle the overflow instead of being clipped), which never becomes definite. Fixed by making `.content` (which does have a real, flex-derived height) a size query container and giving the section `min-height: 100cqh` directly, skipping the indeterminate `.frame` link; `.frame` then also fills, since it simply wraps the now-correctly-sized section. Verified against the coordinator's own `probe-dock-fill.mjs` at 320/390/1440, open and closed, and the same assertions were copied into `scripts/check-contact-transition.mjs`; confirmed they fail against the reverted (pre-fix) CSS before restoring the fix.

## Limits (honest)

- Verified only against Chromium 151 (this environment's Playwright browser) and Chrome's stated 147+ support window. Safari and Firefox don't support `Element.prototype.startViewTransition`; they take the reduced-motion-style instant fallback (verified functionally — there is nothing to see, which is the intended behavior, not a smoothness claim).
- The leaf fade's old/new windows touch at a single instant with zero duration, not a sustained gap — but this was judged by measurement and pixel review at a handful of sampled frames, not profiled continuously across every viewport/duration combination for perceptibility.
- The frame's height animation and the native panel-group animations are independently-driven mechanisms aimed at the same target duration/easing, aligned by copying a native animation's `startTime` onto the height animation. This is not a spec-guaranteed coupling; if either duration source changes independently in the future, they could drift.
- No performance/60fps claim is made. Native View Transitions do their own screenshot-based compositing, a different performance model than the 60fps-animation skill's transform/opacity guidance; CPU-idle profiling was left to the coordinator per the original brief.
- Rapid re-clicks are handled by `skipTransition()` (snap the superseded transition to its target) followed by starting a fresh transition for the latest intent, not by continuously retargeting the in-flight animation. This is confirmed correct (no stale state, no errors) and reasonably quick, but it is a skip-and-restart, not a smooth reversal of motion already in progress.
